== Concepts

The format provides information on current and planned closures and traffic restrictions on the road
network of the Czech Republic: roadworks, closures, diversions, speed limits and changes of traffic layout.

IMPORTANT: The format is a subset of the `x-format:cz-ndic_d2-common-v2.0` format, where closures and roadworks are
published together with other events. The restrictions profile selection is derived from the common
selection by limiting it to road operator actions (`sit:OperatorAction`); the structures and rules are the same
in both formats.

The format is based on the DATEX II publication `sit:SituationPublication` <<EN16157-3>>. It uses the DATEX II 3.7 model without national extensions. No status
information is part of the publication.

[[obalka]]
=== Envelope and publication header

Each message is a DATEX II 3 document with the root element `d2:payload`. The `@xsi:type` attribute of the root element
specifies the publication type (here `sit:SituationPublication`), the `modelBaseVersion="3"` attribute
the model version and the `@lang` attribute the default language of texts.

The format the message conforms to is identified solely by attributes of the root element:

[horizontal]
`@profileName`:: format identifier without version (`cz-ndic_d2-restrictions`),
`@profileVersion`:: format version (`2.0`).

The publication header contains:

* `feedType` – identifier of the data source (distribution) in the register of the national access point <<nap>>; the format of the message is identified
  by the `@profileName` and `@profileVersion` attributes, not by `feedType`; the `feedDescription` element is not used.
* `publicationTime` – time the publication was generated; it changes with every generated publication, even if the
  content has not changed. If a file is made available outside regular generation (assembled from the previous
  content without a change), `publicationTime` does not change; only the time the file was made available changes.
* `publicationCreator` – publication provider:
** country code in lower case (`cz`),
** provider abbreviation (`nationalIdentifier`).
* `headerInformation` – handling of the information; NDIC always sets:
** `confidentiality` = `noRestriction`,
** `informationStatus` = `real`.

All times in the message include the time zone.

=== Situations and situation records

Each event is described by a `situation` element with a unique identifier (`@id`). A situation may evolve
over time; it contains the time of its last change `situationVersionTime` and the `headerInformation`
header.

----
include::{samplesdir}/restriction.xml[tag=situation-head,indent=0]
  ...
</sit:situation>
----

The information itself is carried by `situationRecord` records. A situation may contain several records,
each of a different type (`@xsi:type`) – typically roadworks and their consequence (e.g. a
road closure or alternate one-way traffic). The record identifier is derived from the situation identifier and the record type; a situation therefore contains at most one record of each type.

[[verzovani]]
==== Versioning

* Each record carries a version number (`@version`), the creation time of its first version
  `situationRecordCreationTime` and the creation time of the current version
  `situationRecordVersionTime`.
* Each change of a record increases its version by one and changes `situationRecordVersionTime`.
* In version 3 of the model a situation has no version number:
** its version is expressed by `situationVersionTime`, which always equals the latest
   `situationRecordVersionTime` of its records,
** each change of a record is therefore also a new version of the situation.

* `probabilityOfOccurrence`:
** `certain` – an event that has occurred and also a planned event (its validity starts in the future, see
   <<platnost>>),
** `probable` – information not yet verified (a preliminary report from an unconfirmed source),
** `riskOf` – an impending phenomenon that may or may not occur.
* `safetyRelatedMessage` – `true` marks safety-related traffic information (SRTI).
* `source` – originator of the information, who created it and is responsible for its correctness (`sourceIdentification`,
  where applicable `sourceName`).
* `generalPublicComment` – free-text description of the event by its originator, usually in Czech. It is given
  in every record of the situation (usually the same text), so that each record can be understood on its own.
* `urlLink` – link to a web page with details of the event (`urlLinkType` = `html`).

=== Record types

The format uses only records of the road operator action type (subclasses of `sit:OperatorAction`):

[cols="2,3",options="header"]
|===
|Area |Record types
|Roadworks |`sit:ConstructionWorks` (construction works), `sit:MaintenanceWorks` (maintenance)
|Closures and traffic layout |`sit:RoadOrCarriagewayOrLaneManagement`
|Diversions |`sit:ReroutingManagement`
|Speed limits |`sit:SpeedManagement`
|Other traffic management |`sit:GeneralNetworkManagement`, `sit:GeneralInstructionOrMessageToRoadUsers`
|===

A situation typically contains the cause (e.g. roadworks) and its consequence (e.g. a closure or
alternating one-lane traffic) as two records.

For road operator actions, `complianceOption` specifies whether the measure is mandatory (`mandatory`) or
advisory (`advisory`).

The impact on traffic is described in the `impact` element – by an estimate of the remaining road capacity
(`capacityRemaining`, 0 for a full closure), by the number of operational (`numberOfOperationalLanes`) or
restricted (`numberOfLanesRestricted`) lanes, or by the delay (`delays`).

[[platnost]]
=== Validity

Validity is given for each situation record separately in the `validity` structure. Only
`validityStatus` = `definedByValidityTimeSpec` is used, with the interval `validityTimeSpecification`
(class `com:OverallPeriod`) with the start `overallStartTime` and the end `overallEndTime`.

If an event applies only in a certain part of the day (e.g. works only during the day, at night or
outside rush hours), the interval is supplemented by the `validPeriod` element: the period name
`periodName` and the daily time period `recurringTimePeriodOfDay` (`startTimeOfPeriod`,
`endTimeOfPeriod`); times of the daily period are Czech local time (CET/CEST) without offset, and if
`endTimeOfPeriod` is earlier than `startTimeOfPeriod`, the period spans midnight. An event recurring in another way (e.g. only on some days) is described by several
consecutive records. The validity interval may lie in the past, the present
or the future.

An event is published with its expected or planned end (`overallEndTime`), which the provider refines with new
versions of the record as the situation develops. The event ends either when its validity expires (it ended as
planned), or the provider ends it earlier by setting the end of validity to the time of the message. The format
contains no status or periodically generated data.

[[polohy]]
== Location referencing

The location is described directly in the message by the `locationReference` element of a type that follows the
shape of the location (table below), most often `loc:SingleRoadLinearLocation` (linear location on a single road). A linear location is also used for
point-like events (e.g. an accident): in ALERT-C the event is projected onto the whole section between
adjacent locations, OpenLR and the Global Network sections describe a short road section at the place of the
event.

The location type follows its shape. A linear location `loc:SingleRoadLinearLocation` is always a
contiguous section of *one road* – a numbered road or a named street – and all methods describing it
describe the same section.

[cols="3,3",options="header"]
|===
|Shape of the location |Type of `locationReference`
|contiguous section of one road |`loc:SingleRoadLinearLocation`
|contiguous route over several roads |`loc:ItineraryByIndexedLocations` (<<trasa>>)
|non-contiguous or branching location, one-off area |`loc:LocationGroupByList` (<<skupiny>>)
|recurring area |`loc:LocationGroupByReference` (<<skupiny>>)

|===

A location is usually described by several methods at the same time, depending on their availability at
the given place; all of them describe the same real-world section. At least one method must be given. All methods are part of the DATEX II 3.7 model.

[cols="2,3,4",options="header"]
|===
|Method |Element |Use
|ALERT-C |`alertCLinear` (`loc:AlertCMethod2Linear`) |where a location exists in the ALERT-C location table
|OpenLR |`openlrLinear` |always, where the location can be encoded (dynamic location referencing)
|Road chainage |`linearWithinLinearElement` with `roadNumber` |roads with chainage
|Global Network |`linearWithinLinearElement` with `loc:LinearElementByCode` |sections of the Global Network (ŘSD)
|Location path |`gmlLineString` |line in ETRS89 for display on a map; the only exact coordinates of the start and end of the location (<<prubeh>>)
|===

The affected carriageway, lanes or kind of place (e.g. a bridge) are specified by
`supplementaryPositionalDescription` (<<upresneni>>).

IMPORTANT: The location referencing methods are described identically in all NDIC formats that use them.
Graphical illustrations of the methods (ALERT-C locations and direction, bidirectional location in OpenLR, location
composed of Global Network sections) are given in the documentation of the format `x-format:cz-ndic_d2-pls-v2.0`,
chapter Location referencing.

=== ALERT-C location referencing

include::{kitdir}/shared/en/poloha/alertc.adoc[]

.ALERT-C location referencing – direction, secondary and primary location
image::alertc-poloha-en.svg[ALERT-C – direction and locations,width=680,align="center"]

In messages about events the following also applies:

* According to the ALERT-C principle, the primary location is the place where the event occurred (e.g. the
  head of a queue), the secondary location the end of the affected section (e.g. the end of the queue).
* `alertCAffectedDirection` = `both` expresses an event valid in both directions of travel.
* If an event runs over several roads, each part of the route (<<trasa>>) or member of the group
  (<<skupiny>>) has its own `alertCLinear`.
* A point-like event:
** between two locations (e.g. an accident on a section) is described by the whole section between
   adjacent locations,
** only an event at an ALERT-C location point, usually in the middle of a junction, has identical primary
   and secondary locations.

[[upresneni]]
=== Supplementary positional description

The `supplementaryPositionalDescription` element specifies which part of the road the event affects. It applies
to the whole location and all methods describing it:

* `carriageway` – the affected carriageway and the affected lanes in it:
** carriageway `carriageway`, e.g.:
*** `mainCarriageway` – main carriageway,
*** `entrySlipRoad` – entry slip road,
*** `exitSlipRoad` – exit slip road,
** lane `lane/laneUsage`, e.g.:
*** `rightLane` – right lane,
*** `leftLane` – left lane,
*** `middleLane` – middle lane,
*** `hardShoulder` – hard shoulder,
** without a lane, the event affects the whole carriageway.
* `infrastructureDescriptor` – the kind of place on the road, e.g.:
** `onBridge` – on a bridge,
** `atServiceArea` – at a service area.
* `geographicDescriptor` – the position in the terrain, e.g. `onBorder` (at the state border).
* `lengthAffected` – length of the affected section in metres if the source gives only the length (e.g. a restriction
  2 km long).

[[trasa]]
=== Location on more than one road

If a contiguous location passes from one road to another (e.g. a closure along a second-class road and the
adjoining third-class road), it is described as a route – `locationReference` of type
`loc:ItineraryByIndexedLocations`:

* Each part of the route lies on one road:
** it is a `locationContainedInItinerary` element with the `@index` attribute (1, 2, …),
** its `location` element is a linear location `loc:SingleRoadLinearLocation` described by GN sections
   and its own location path `gmlLineString`; OpenLR and ALERT-C are given where they can be encoded for that part
   (ALERT-C locations cover only part of the road network).
* The parts are in the order of travel (for a bidirectional location in the order of the first direction);
  the end of a part is the start of the next one and the parts do not overlap. Directionality is the same in
  all parts.
* A section of another road inside a junction, a short connecting link or two concurrent roads do not start
  a new part. If the location has an ALERT-C description, each part corresponds to one path of the ALERT-C
  location table.
* A route has at least two parts. A location on one road is always directly
  `loc:SingleRoadLinearLocation`.

.Route along two roads (sample `closure-route.xml`, shortened)
[source,xml]
----
include::{samplesdir}/closure-route.xml[tag=itinerary,indent=0]

always refers to one road: each part with `alertCLinear` can be converted separately into an RDS-TMC message
with the same event.

[[skupiny]]
=== Area events and groups of sections

A location whose sections form neither one contiguous section nor a route – a closure of a junction
including its arms, a network of streets, sections with gaps (also on one road) or an area phenomenon
(closure of an area, an event, a calamity) – is described by one record whose location is a group of
sections:

* *One-off area* – `locationReference` of type `loc:LocationGroupByList`:
** the individual sections are in `locationContainedInGroup` elements (at least two),
** each section lies on one road and is described as a separate linear location
   (`loc:SingleRoadLinearLocation`) by GN sections and the location path; OpenLR and ALERT-C are given where
   they can be encoded for that section (ALERT-C locations cover only part of the road network),
** the order of the sections has no meaning.
* *Recurring area* (regular winter closures, permanent diversion routes) – reference to a predefined group
  of the `x-format:cz-ndic_d2-pls-v2.0` format:
** `locationReference` of type `loc:LocationGroupByReference`,
** with `predefinedLocationGroupReference` (`@targetClass` = `loc:PredefinedLocationGroup`).

An area is always described by a list of linear sections.
